# Shared identity session logout and revocation

Status: accepted engineering contract. Local API support now includes signed back-channel logout and RP-initiated browser sign-out. PostgreSQL/API checks cover one-use logout state, exact redirects, local session clearing, replay denial and provider outage handling. Real local Keycloak browser delivery, Google behavior, physical devices and production configuration remain open; this is not rollout approval.

## Problem

VMMS creates its own staff and vehicle-owner sessions after validating a central OIDC sign-in. A later logout at the identity provider does not currently invalidate those application sessions. The current eight-hour local expiry therefore outlives some central sign-out and account-revocation events.

## Required behavior

1. Each OIDC-created local session records the validated issuer and client, a privacy-preserving hash of the provider subject, an optional hash of the provider session ID (`sid`), and the verified ID Token issue time. Raw ID Tokens and refresh tokens are never stored or sent to browser JavaScript.
2. The VMMS browser sign-out command removes both staff and owner sessions in that browser transaction before starting central sign-out through the discovered RP-Initiated Logout endpoint. Local-only audience DELETE routes remain available. The provider return uses a server-generated exact URI and a server-owned destination enum; request input cannot choose an arbitrary return URL.
3. The back-channel URL is `/api/v1/auth/oidc/backchannel-logout`. It accepts only form-encoded OIDC Logout Tokens validated against the configured issuer's discovered JWKS and VMMS client ID. Validate RS256 signature, issuer, audience, time bounds, `jti`, `events`, subject/session targeting, and absence of `nonce`; reject unsupported algorithms and malformed or oversized form bodies. Cache issuer discovery, refresh signing keys through the JOSE remote-JWKS cache, and rate-limit requests before token verification.
4. Process each logout `jti` once. In one database transaction, record replay protection, add a revocation barrier for the targeted `sid` or `sub`, and delete matching staff and owner sessions for this issuer/client. An event with both `sid` and `sub` must match both. A session-only logout must not invalidate other sessions for that subject.
5. Prevent login callbacks that race a logout event from creating a session afterward. Session creation compares the verified ID Token issue time with unexpired subject/session revocation barriers inside the same transaction. A later successful authentication may establish a new provider session.
6. Local logout, provider logout delivery, session revocation, central account disablement, and lost-authenticator recovery are separate claims with separate evidence. Do not assume disabling an account or removing a passkey emits a logout event; document the administrator's explicit session-revocation action and test it against the configured provider.

## Data and transaction boundary

Staff and owner sessions share one VMMS OIDC client but retain separate local cookies and authorization rules. Back-channel logout may invalidate sessions in both audiences when they belong to the same exact provider session. It never changes staff memberships, owner relationships, or business grants.

Store hashes of provider subjects, session IDs and issuer/client-scoped logout `jti` values. Keep barriers only long enough to cover the maximum accepted ID Token/session lifetime plus clock tolerance. Cleanup is bounded and cannot make expired login transactions valid again. The database runtime role may insert the logout receipt/barrier and delete matching sessions only through narrowly scoped SQL functions; no provider token or identity admin API is exposed to normal application code.

## Verification contract

Use real PostgreSQL with the non-owner runtime role. Verify valid session and subject logout; duplicate `jti` idempotency; wrong issuer/audience/signature, unsupported algorithm, missing event, `nonce`, expired/future token, malformed form and unrelated subject/session denial; callback/logout races; and preservation of unrelated users, other provider sessions, memberships and relationships. Verify staff and owner cookies fail on their next protected request after an applicable event.

The local RP-initiated route is `POST /api/v1/auth/oidc/logout`. It requires a same-origin CSRF token and an active local staff or owner session, clears both VMMS browser sessions transactionally, and only then builds the provider redirect. The provider URL is created through `openid-client` from exact discovered metadata using `client_id`, the configured callback and random state; it does not include an ID or refresh token or trust an unsigned `sid`. Logout state and browser binding are hashed in a narrow database-owned table and atomically consumed once by the exact callback. The callback destination is a fixed server-owned value (`signed-out`, `staff` or `owner`). Existing local-only DELETE routes remain available as an escape when provider logout cannot be started.

Current local API evidence covers signed token validation against synthetic issuer JWKS, malformed form rejection, runtime-role PostgreSQL processing, replay, bounded cleanup, subject-only/session-only/combined targeting, unrelated session preservation, stale login callbacks, and browser sign-out state replay/binding. The standalone browser callback has not yet been exercised with the real local Keycloak client. The local VMMS client registration script now configures an exact post-logout callback, but its latest invocation failed without a safe provider error code; registration and browser behavior remain unverified. Run a loopback provider/browser check proving sign-out and account switching without manually clearing identity-provider cookies. Separately exercise provider-initiated logout and the explicit administrator procedure for account disablement/passkey loss. Use synthetic accounts only. Production HTTPS, callback reachability, actual `TRUSTED_PROXY_CIDRS`, edge configuration, Google federation, physical devices and operational ownership remain separate launch gates.

The protocol follows [OpenID Connect Back-Channel Logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html) and Keycloak's [back-channel logout behavior](https://www.keycloak.org/docs/latest/server_admin/index.html#_oidc_clients). The application owns the provider-to-product session mapping; the identity provider never supplies VMMS business authorization.
