# Sensitive work-order detail reads

## Scope

The implemented staff read-audit slices record successful preparation of (1) a staff work-order detail projection, and (2) the paged work-order queue plus vehicle, paying-client and party lookups. Owner vehicle-list reads have a separate metadata-only audit contract in [owner vehicle read audit](owner-vehicle-read-audit.md). Other sensitive lists, exports, and audit review remain open. The broader `R-M-0175` requirement remains in progress; protected exports remain gated by `REV-027`.

## Transaction and authority

`GET /api/v1/sites/:siteId/work-orders/:id` calls `readWorkOrderDetail`. The function opens the existing scoped transaction, rechecks and share-locks active membership through `lock_membership`, share-locks the site-scoped work-order root, builds the existing projection, inserts one metadata event, and commits before returning the projection. Active read-only staff are allowed. Missing membership or work-order scope is denied. An audit insert or commit failure prevents the response from returning protected detail.

The work-order lock stabilizes the root and its version against cooperating commands while the projection is assembled. The projection joins other records and uses multiple queries; this slice does not claim a serializable snapshot of every related record.

## Event fields and access

`work_order_read_events` stores opaque organisation, site, actor and work-order IDs; fixed action and projection revision; root version; server-generated UUID request ID; and database timestamp. It stores no customer field values, names, phone/email, VIN, registration, complaint text, request URL/query, IP, user agent, payload or free-form purpose. The identifiers remain linkable metadata and are not anonymous.

The API runtime can insert only under matching transaction-local organisation, site and actor scope. It cannot select, update, delete or truncate the table. A trigger rejects updates and deletes. Database owners remain a separate administrative trust boundary.

`sensitive_read_events` records only organisation, site and staff actor IDs; one fixed action (`work-order-queue-read-prepared`, `vehicle-lookup-read-prepared`, `client-lookup-read-prepared`, `party-lookup-read-prepared` or `workforce-organogram-read-prepared`); projection revision 1; returned record count; a server-generated request UUID; and a database timestamp. The result count is the number of records in the response page or lookup result, never the queue's total match count. Empty results produce a zero-count event. It does not store the query, VIN, returned values, route, client request ID or free-form metadata.

Each queue/lookup read locks and rechecks active site membership inside the same transaction as the data query and audit insert. The organogram projection additionally requires an active Head of Service Centre role and write-enabled site membership. Missing or revoked membership is denied. An audit write failure rolls back and withholds the projection. Runtime INSERT is granted only for the seven input columns; event ID and timestamp remain database-generated. Forced RLS validates transaction-local actor and site scope, and the event table is immutable to runtime access.

The action suffix `read-prepared` means the server prepared and committed the projection before responding. It does not prove response delivery or human viewing. These metadata events identify the actor, site, read category, time and number of returned records but cannot reconstruct which parties or vehicles were included.

## Request log privacy

Fastify request logs serialize only the HTTP method and matched route template, excluding raw URL, query, request headers, and route values. Request IDs are generated by the server, and caller-supplied request-ID headers are ignored. This prevents client/VIN lookup query values from entering default request logs.

## Limits and follow-up

Each read is a separate event; the work-order screen currently polls details while evidence processing. Measure resulting volume and define retention before production; do not expire events automatically without the approved retention policy. Add separate audit coverage for other sensitive read paths. Continue export authorization and review design only after owner decisions in `REV-027`.
